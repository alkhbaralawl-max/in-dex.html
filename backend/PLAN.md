# خطة التنفيذ الخادمي

## البنية المستهدفة
- Cloudflare Worker كواجهة API وحيدة للموقع ولوحة المشرف.
- Cloudflare D1 كمخزن بيانات للحسابات والجلسات والألعاب والمباريات والتذاكر وسجل الأرصدة.
- Cron Trigger لتحديث بيانات المباريات في الخلفية.
- مزود نتائج كرة قدم مع كاش مشترك وحد استخدام يومي صارم.

## استهلاك بيانات الكرة
- الحد الداخلي: 50 طلبًا كحد أقصى خلال 24 ساعة متحركة.
- استخدام طلب جماعي للمباريات بدل طلب لكل فريق.
- تحديث جماعي كل 30 دقيقة أثناء وجود مباريات نشطة، والتوقف بعد اكتمالها.
- حفظ الاستجابة في كاش مشترك؛ زوار الموقع لا يستدعون مزود النتائج مباشرة.
- ترك احتياطي للمحاولات الفاشلة والطوارئ وعدم تجاوز الحد أبدًا.

## لوحة التحكم ونسبة عائد كل مباراة
- إعداد `profitPercent` لكل مباراة قبل بداية المباراة.
- حفظ `kickoffAt` كطابع زمني واضح، وليس نص موعد فقط.
- الخادم يرفض تعديل معامل العائد بعد `kickoffAt`.
- كل تذكرة تحتفظ بالمعامل الذي كان ساريًا وقت تسجيلها.
- التسوية على الخادم وبمعرّف عملية فريد لمنع إضافة العائد مرتين.

## الأمان
- كلمات المرور لا تُقرأ ولا تُحفظ كنص صريح.
- جلسات خادمية عبر Cookies آمنة HttpOnly وSameSite.
- صلاحيات مستقلة للاعب والمشرف.
- لا يسمح للمتصفح بتعديل الرصيد أو نتيجة اللعبة مباشرة.
- مفاتيح مزود النتائج وقاعدة البيانات داخل Worker Secrets فقط.
- سجل تدقيق لكل تغيير في الرصيد والمعاملات وإدارة المباراة.

## مراحل الانتقال
1. إنشاء مخطط D1 وترحيل تجريبي للبيانات مع الاحتفاظ بنسخة Firebase.
2. إنشاء مصادقة اللاعبين والمشرف على Worker.
3. نقل العمليات المالية الافتراضية والتذاكر والتسويات إلى Worker.
4. نقل منطق الألعاب ونتائجها إلى Worker.
5. تشغيل خدمة النتائج المجدولة مع عداد الـ50 طلبًا/24 ساعة.
6. اختبارات صلاحيات وتزامن ومنع التكرار، ثم نشر تدريجي.

هذه خطة وليست ادعاءً بأن النقل الخادمي اكتمل.
